# FitLink — abuse, cost and dependency review

Reviewed 2026-09-08: login, sign-up, password reset, public forms, uploads,
webhooks and every paid route, for abuse and cost amplification; plus the
dependency trees of the app and the website against current advisories.
Each item carries evidence, a reproducible test, the control now in place,
and the risk that remains. Proofs:

```
python supabase/security/run_audit.py supabase/security/abuse_controls.sql   # database-level limits
npm audit --omit=dev            # app   (also in CI, advisory)
npm audit --omit=dev --prefix C:/projects/fitlink                             # website
```

Two facts the controls rest on, both probed against the live project:
PostgREST hands the caller's address to SQL (`request.headers` →
`x-forwarded-for`), so anonymous routes can be limited per address inside
the database (`request_ip()`); and `check_key_rate_limit` rows written inside
a refused transaction roll back with it, so the proofs leave no residue.

## Findings

| # | Surface | Risk found | Evidence | Test | Control | Remaining risk |
|---|---------|------------|----------|------|---------|----------------|
| C1 | Paid AI routes: `generate-workout`, `generate-diet`, `generate-exercise`, `rewrite-exercise` | Any signed-in account could call them — an athlete account is free to create in bulk, and per-account limits do nothing against a farm of accounts (30–40 calls/hour each). | Functions checked only `requireCaller` + per-user `guardRate` (grep 2026-09-08: no role or entitlement check). | Sign in as an athlete, call `generate-workout` → now `403 coaches_only`. | Coaches only (a `trainers` row), plus a **platform-wide daily ceiling** per bucket (`global` in `_shared/rateLimit.ts`, 1,500/day each) that refuses with 503 `capacity`. | A farm of coach accounts can still reach the ceiling; the ceiling is the bill's hard cap (about 1,500 model calls per feature per day). Raise it when real usage asks. |
| C2 | `food-image` (Spoonacular), `coach-assistant`, `solo-corner`, `solo-program`, `text-to-speech` | Same amplification through account farming; `text-to-speech` solo mode had no premium check and no text cap, and ElevenLabs bills per character. | `text-to-speech/index.ts` read `text` with only an empty check; solo branch had no entitlement gate. | Call `text-to-speech` with `mode:'solo'` from a non-premium athlete → `402 premium_required`; with 1,300 characters → `400 text_too_long`. | Global ceilings (food-image 2,000/day, coach-assistant 1,500, solo-corner 3,000, solo-program 500, solo-voice 5,000, exercise voice 3,000); solo voice requires `premium_until`; text capped at 1,200 characters. Corner and program were already premium-gated. | Legitimate peaks hit the ceiling before the bill does; the 503 tells the app to try tomorrow. Exercise-cue voice is cached by hash, so repeats cost nothing. |
| C3 | Push relay `send-push-notification` | A linked person could be pushed without limit (a coach's phone buzzing 10,000 times from one athlete). | No `guardRate` in the function (grep). | Loop the call 61 times in an hour as an athlete → 429. | 60/hour, 300/day per caller (`push` bucket, fail-open on limiter outage since it is not a paid call). | Sixty notifications an hour is still annoying; blocking the sender is a product feature, not a limit. |
| C4 | Coach contact lookup `search-unassigned-clients` | Exact-match probing of contacts, unlimited. | No rate limit (grep). | 31 lookups in an hour as a coach → 429. | 30/hour, 100/day per coach. | A patient prober learns one name and avatar per confirmed contact; the contact must already be known. |
| C5 | Direct-message floods (`messages`) | No server-side rate: a user could insert thousands of rows a minute, each fanned out over realtime and push. | `messages` had no rate trigger (trigger dump). | `abuse_controls.sql`: the 301st message in an hour is refused; five in a row pass. | `rate_limit_writes` BEFORE INSERT: 300/hour, 2,000/day per account. | Three hundred an hour is still a lot of noise for one recipient; conversation muting is the product answer. |
| C6 | `notifications`, `conversations`, `coach_reports`, `live_class_messages` | Same class: unbounded inserts by any signed-in user into another person's inbox, report queue or class chat. | Trigger dump: only live chat had a 1-per-second check. | Sixth coach report in a day refused (`abuse_controls.sql`). | 120 notifications/hour, 50 conversations/day, 5 reports/day, 300 live-chat lines/hour per account. | Limits are per account; account farming remains bounded only by sign-up throughput (C10). |
| C7 | Public form `waitlist_signups` (anonymous insert) | Unlimited rows from anyone; the same address any number of times. | Policy allowed any well-formed email, no limit, no uniqueness. | Two inserts of the same address leave one row; a sixth in an hour from one address is refused. | `waitlist_dedupe` (repeat is a quiet no-op) + 5/hour per address. | An attacker rotating addresses and IPs can still grow the table slowly; it is a mailing list, not money. |
| C8 | Anonymous RPCs `lookup_client_by_contact`, `invite_public`; edge `invite-info` | Unlimited enumeration of whether a contact is on FitLink, and code guessing. | Both callable with the anon key with no limit; `invite-info` had 60/hour per address. | The 31st call from one address is refused (both, `abuse_controls.sql`); HTTP burst on `invite-info`: first 429 at request 61 of 70 (2026-09-08). | 30/hour per address on both RPCs (`api_rate_ok`); `invite-info` keeps 60/hour. | Codes are 31⁶ ≈ 887 million; at 30 guesses an hour per address, guessing is not a strategy. |
| C9 | `request_coach` churn | Request → cancel → request wrote a conversation, a message and a notification to a coach every round. | Function had no limit. | Eleventh request in a day returns `rate_limited` (`abuse_controls.sql`). | 10 requests/day per athlete. | Ten intro messages a day to coaches is the ceiling of nuisance from one account. |
| C10 | Sign-up, login, password reset, phone code | Account creation and OTP sending are the amplifiers behind every per-account limit above; SMS costs real money per code. The app sends no CAPTCHA token (`context/AuthContext.tsx:223-259`, `app/(auth)/client-signup.tsx:232-268`, `app/(auth)/login.tsx:143`). | Supabase Auth defaults: 30 OTP SMS/hour project-wide, 1 per 60 s per number, 30 token requests per 5 min per IP, 30 emails/hour with the built-in SMTP. | Operator test: request 6 codes for one number inside a minute → the 2nd is refused (60 s cooldown); 31 sign-ups from one address in 5 minutes → 429. | **Operator settings**: enable Turnstile CAPTCHA on sign-up and OTP, keep the per-number cooldown, set the SMS hourly cap to real demand, minimum password length 8, leaked-password protection. The app already retries only transport errors, never 429s (`lib/authErrors.ts`). | Until CAPTCHA is on, account farming is limited only by Auth's IP rate limits; every per-account control in this review assumes accounts are not free at scale. |
| C11 | Uploads | Four buckets had no size ceiling or type list (`avatars`, `chat-attachments`, `diet-images`, `progress-photos`, plus the three server-written ones). | `storage.buckets` columns null. | `abuse_controls.sql`: zero unbounded buckets. | 5–15 MB images, 200 MB exercise video, MIME allow-lists on every bucket. | Per-object limits only; a user can still upload many files. Storage is cheap and per-user quotas need an object-count trigger later. |
| C12 | Webhooks | Mux verified the signature but not its age: a captured delivery could end a class or delete a stream a day later. Stripe (`constructEvent`, 300 s) and RevenueCat (forward-only grants, guarded revokes, dedupe by event) were fine. | `mux-webhook/index.ts` verify function, pre-fix. | Replay a signed Mux payload older than five minutes → refused. | 300-second window on the Mux signature timestamp. | RevenueCat carries no timestamp; its handler cannot be replayed into a grant it did not already make, only re-affirm one. |
| C13 | Mux live streams | Failed go-live attempts leave streams behind; idle streams are free, live minutes are not. Elite coaches can create 20/hour. | Memory of four orphaned streams; `create-mux-stream` limit 20/hour. | — | Streams are deleted on disconnect by `mux-webhook`; creation is Elite-only and rate-limited. | Orphans are clutter, not cost; a monthly cleanup of streams with no class is housekeeping. |

| C16 | Edge-function module pins | `@supabase/supabase-js@2` floated to whatever esm.sh served at deploy time; three functions pinned three different versions. | grep of 21 imports. | grep: all 21 now `@2.105.3`. | Pinned to the app's version. Deno `std@0.168/0.177` and `stripe@14` are old but carry no advisory relevant here. | A pin protects deploys from a bad upstream release, not from a compromised one; Dependabot does not cover esm.sh imports, so bump by hand with the app. |

## Not an issue

- **Login brute force**: Supabase Auth's token endpoint limit (30 per 5 minutes per address) plus the leaked-password check (operator) cover it; the app shows generic errors and never distinguishes "no such user".
- **Password reset**: one email per address per cooldown at Auth; the reset link is Supabase's signed token.
- **Stripe routes**: `create-subscription` is idempotent per athlete-plan-hour and refuses a second live subscription; Connect account creation is free and self-only.
- **`invite-info` logging**: never logs the code and the address together.
